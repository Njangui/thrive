# C4 — Modèle de pages du site par blocs (étape 3, partie données)

## Décisions
- **Un site = un instantané versionné** (`site_versions.snapshot`, jsonb) : thème + navigation + pages + blocs. Un tenant a au plus 1 brouillon, 1 version publiée, N archivées (index uniques partiels). Publier et restaurer sont atomiques ; l'historique n'est jamais réécrit.
- **Publication** = `publish_site_version(org, version, user)` (une transaction : archive la publiée, publie le brouillon). **Restauration** = recopier une version archivée en nouveau brouillon (`source = 'restore'`, `restored_from`), puis la publier (action `sensitive`).
- **Données, jamais du code** : `SiteSnapshotSchema` (`src/domain/entities/site.ts`) est strict (clés inconnues rejetées), sans HTML ni script ; liens = chemin `/…` ou https ; médias = https ; slugs de pages uniques et non réservés (routes du produit) ; exactement un accueil ; navigation → pages existantes.
- **Types de blocs — uniquement ce que la vitrine sait rendre** (le schéma refuse le reste, pour qu'aucun réglage ne soit enregistré, publié et invisible) : **accueil** = les sections du moteur (hero, about, products, services, categories, promotions, gallery, testimonials, team, faq, booking, contact, location, social_links, cta), une fois chacune, sans `text` (les gabarits sectoriels sont monolithiques) ; **page supplémentaire** = `text` (texte brut) et les sections de données autonomes, sans hero, cta ni booking. Les blocs de données n'ont aucun réglage propre : leurs intitulés viennent du modèle du secteur ; un titre/sous-titre/limite ne sera ajouté au schéma que le jour où un composant le lira.
- **Compatibilité** : `buildDefaultSiteSnapshot` (pur) génère l'accueil d'un tenant existant à partir de `getLandingConfig` : mêmes sections, même ordre ; sections désactivées conservées en `visible: false`. Navigation vide = la navigation actuelle du produit s'applique.

## Droits (migration 0162) — validés par Marc-well
- Lecture : tout membre du tenant.
- Création/modification de **brouillons** : owner, admin, manager (et tout membre ayant reçu `publish_site`).
- **Publier / restaurer / archiver** : owner et admin par défaut ; **le propriétaire peut accorder ce droit à n'importe quel membre** via `memberships.extra_permissions = {"publish_site": true}` (seule la valeur booléenne `true` compte). Même règle en SQL (`can_publish_site`) et dans le code (`site-permissions.ts`: `requireSitePublisher` / `requireSiteEditor`, sans toucher à `auth-service`).
- Triggers : contenu d'une version publiée/archivée immuable ; archivée ne revient jamais ; publiée ne repasse pas en brouillon (valable aussi pour le service-role).
- **Attention** : les services applicatifs utilisent le service-role, qui contourne la RLS. La barrière réelle est `requireSitePublisher` (+ confirmation `sensitive` côté agent, C1) ; la RLS est un filet pour tout accès par client utilisateur.
- **À traiter hors C4 (C2 identité / droits)** : aujourd'hui `extra_permissions` n'est lu par aucun code et aucune interface ne permet de l'accorder. Il faut une action « accorder le droit de publier » **réservée au propriétaire** (la politique RLS actuelle de `memberships` laisse owner ET admin modifier une ligne, donc un admin pourrait aussi accorder ce droit : à restreindre dans cette action). À inscrire dans `ROLE_TOOL_MATRIX.md` (C1).

## Service, opérations et garde-fou SEO (livré)
- `site-operations.ts` (pur) : opérations d'édition de l'étape 1 — texte/props d'un bloc, visibilité, ordre, thème, titre et SEO de page, barre d'annonce. Atomique (une opération invalide n'applique rien), 50 opérations max par appel, résultat revalidé par `SiteSnapshotSchema`. L'éditeur manuel et l'agent émettent les mêmes opérations : des données, jamais du code.
- `site-seo-lint.ts` (pur) : **bloque** la publication si l'accueil est en `noindex` ou si une page indexable n'a aucune section visible. **Avertit** (sans bloquer) : longueur du titre (15–60) et de la description (70–160), description absente, titres/descriptions en double, texte alternatif du hero manquant, image de partage absente, page orpheline, lien interne vers un chemin inconnu. Les niveaux se règlent dans la table `SEVERITY` (proposition à valider). La règle « plusieurs H1 » a été retirée : le modèle la rend impossible (un seul hero, sur l'accueil ; le titre d'une page supplémentaire est son unique H1).
- `site-version-service.ts` : `getPublishedSite`, `listSiteVersions`, `getSiteDraft`, `editSiteDraft`, `lintSiteDraft`, `discardSiteDraft`, `publishSiteDraft` (bloqué par les erreurs critiques), `restoreSiteVersion` (nouveau brouillon, jamais d'écrasement sans `discardDraft`). Chaque fonction vérifie acteur et tenant ; actions tracées dans `audit_logs`.

## Branchement à la vitrine (livré, par un « pont »)
- **Principe** : on ne réécrit pas le rendu. `site-storefront-bridge.ts` (pur) convertit la **version publiée** en `LandingConfig`, le contrat que consomment déjà `getStorefrontSite` et tous les composants. `site-published-config.ts` (mémoïsé par requête) est appelé dans `getStorefrontSite` ; `generateMetadata` de `app/page.tsx` y lit le SEO publié de l'accueil.
- **Zéro impact tant que rien n'est publié** : sans version publiée, la config est renvoyée telle quelle. Toute erreur de lecture = repli sur la config actuelle (la vitrine ne casse jamais à cause du nouveau modèle).
- **Parité de rendu** : un test d'aller-retour (config → snapshot par défaut → config) vérifie que sections, ordre, visibilités, hero, thème, annonce et promesses sont identiques. Le brouillon par défaut reprend aussi le SEO ACTUEL de l'accueil (`resolveOrganizationSeo`), donc le garde-fou juge ce qui s'affiche réellement.
- **SEO d'accueil publié** : titre, description, image de partage et `noindex` surchargent ceux de l'organisation ; champ absent = SEO actuel conservé.
- **Pages supplémentaires (livrées)** : route `/(site)/[pageSlug]` (`/<slug>`), qui ne sert que la version PUBLIÉE ; les routes statiques l'emportent toujours et les slugs réservés sont refusés (un test compare `RESERVED_PAGE_SLUGS` à l'arborescence réelle de `src/app`). Rendu par `block-page.tsx` ; le sitemap déclare les pages indexables et retire l'accueil s'il est en `noindex`. **Menu** : les entrées du site s'AJOUTENT au menu du produit (« Contact » reste en dernier), elles ne le remplacent jamais.
- **Limites connues** : `mediaAlt` du hero n'est lu que par le hero générique (`HeroSection`) ; les gabarits sectoriels ont leur propre hero (à vérifier un par un) ; un bloc de données sur une page supplémentaire utilise les composants existants sans réglage ; le public ne voit jamais le brouillon (seule la version publiée est servie) ; dans l'aperçu privé, les liens sont inactifs.
- **Coût** : une lecture supplémentaire par requête de vitrine (1 requête indexée, mémoïsée).

## Éditeur de versions (dashboard, livré)
- Page `/dashboard/site/versions` (+ lien « Versions du site » sur `/dashboard/site`) : créer un brouillon à partir du site actuel, masquer/afficher et réordonner les sections de l'accueil, modifier leurs textes (hero : titre, sous-titre, bouton, lien, description de l'image), référencement de l'accueil avec compteurs de longueur, panneau « Contrôle avant publication » (erreurs bloquantes / conseils), publier (confirmation), abandonner le brouillon, historique et restauration.
- Même garde de plan que `/dashboard/site` (`site_customization`, à partir de Starter). Les boutons sont masqués selon `getSitePermissions`, mais **les droits sont décidés par les services**, jamais par la page.
- **Bandeau d'avertissement** sur `/dashboard/site` quand une version est publiée : ses réglages restent enregistrés mais ne modifient plus la vitrine (la version publiée prime) — sans lui, les modifications y resteraient sans effet et sans explication.
- **Aperçu privé du brouillon** : `/dashboard/site/versions/preview` (`?page=<slug>` pour une page). Rend la vraie vitrine (mêmes composants, vraies données du tenant) avec le BROUILLON, via `getStorefrontPreviewSite` ; réservé aux membres connectés (garde de plan incluse), jamais indexé, liens et boutons inertes (barre d'outils pour changer de page). `getStorefrontSite` a été refactoré en un constructeur partagé (`buildStorefrontSite`) : le chemin public est inchangé, mais **c'est une fonction centrale : lancer `storefront-service.test.ts` et vérifier une vitrine réelle avant déploiement**. Chargeur `loadTenantContextByOrganizationId` ajouté (contexte par identifiant, réservé aux usages authentifiés).
- Éditeur : sections et textes de l'accueil, ajout d'une section absente, pages supplémentaires (création, blocs, menu, référencement, suppression). Thème (couleurs — ou celles du secteur —, police, ambiance) et barre d'annonce sont aussi dans l'éditeur.

## Non couvert par le garde-fou (à faire au rendu ou avec le réseau)
